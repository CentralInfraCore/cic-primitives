## 5. What the check does and the tests that it can fail

`check_g0.py`: **the evidence each prerequisite needs is a contract of the check, independent of the record** (D1 to D6: the specification and the extension review; OP-1: the plan; OP-2: the extension cases, the review, the review document and the vectors, and the check's own table of the path each key must be bound to): a record that empties or drops the `evidence_files` of a prerequisite, declares only part of them, or binds a key to another file cannot pass (an empty list is not a pass). **The base commit:** by default the check verifies only the *declared* commit identifier (a 40-hex id) and the *current* SHA-256 of the bound files, and says so in its output; with `--verify-git` the commit must exist in the repository and every bound file must be, byte for byte, the blob of that commit (the real record passes; a non-existing commit, and an older commit whose tree lacks the files of #53 and #54, fail). The record is well-formed with a source, a date, a channel, a reference and the verbatim statement; every bound file exists and has the recorded SHA-256 (a stale or wrong hash is `INVALID`); every decision of D1 to D8 and OP-1 to OP-4 is recorded once and its status equals the owner's verbatim table (a contradiction is `INVALID`); the plan's `closed_by` of each open point equals the record's; G-0 of the plan still names D1 to D6, OP-1 and OP-2 and **names no later open point**; per prerequisite the decision and the evidence are shown separately; OP-2 is not normative, counts 47 cases, and its accepted cases depend only on confirmed decisions and none on a decision on hold; the recorded specification text of OP-1 must exist, have the recorded SHA-256 and treat at least the topics of OP-1 (YAML 1.2, core schema, tags, duplicate keys, aliases, merge keys): **a lower bound on presence, not a judgement of the content, which only review can give**; a closure record is accepted only if it is an owner closure of G-0, names the digest of the decision record, and the prerequisites are all met, **so no closure record can turn a missing or stale OP-1 evidence into `CLOSED`** (it makes the verdict `INVALID`). Verdicts: `INVALID`, `NOT_READY`, `READY_FOR_OWNER_CLOSURE`, `CLOSED`; exit 0 only for the last two.

`selftest_g0.py` (49 checks): the real state (exactly one unmet item; OP-3 and OP-4 do not block); two positive controls in a temporary root with a **fixture** of the OP-1 text (a complete package is `READY_FOR_OWNER_CLOSURE`; with a valid closure record it is `CLOSED`); **41 planted faults**, each applied to the complete package and counted only when the verdict is the expected one (never READY or CLOSED), the exit is 1, and the intended `FAIL-EXPECT` line is printed; **for 39 of them the whole set of failures is compared** (not only the needle), so a fault that has exactly the expected causes and no others is what counts (the two cascades of 29 and 40 labels keep the needle only): a missing decision, a contradictory record, a record that disagrees with the owner's statement (two), missing provenance (two), a wrong SHA-256, a bound file changed after the decision, an unmet prerequisite, a changed OP-1 text, a prerequisite not confirmed, accepted cases that depend on a decision on hold (two), OP-2 treated as normative, a wrong case count, OP-3 closing at G-0, OP-3 without its precondition, a plan that demands a later open point at G-0, a plan that no longer names OP-2, an unknown decision, an OP-1 text that does not treat the aliases, and three closure faults; and the branches added after the first review of this package: a decision the statement does not mention, a wrong record format, a base commit that is not a commit id, a bound file that does not exist, evidence that names an unbound file, a missing OP-1 specification path, OP-1 not decided, OP-2 on hold, the OP-1 and OP-2 decisions missing, and an accepted case that depends on a decision the owner did not confirm (and that is not on hold); and, after the third review round, the evidence contract: an empty evidence list for D1, for OP-1 and for OP-2, a removed `evidence_files` field, evidence that omits the extension review, and a key bound to another existing file with a correct digest; three further checks run with `--verify-git` on the real files (the real record passes, a non-existing commit, an older commit that lacks the files of #53 and #54) (without evidence, wrong digest, not an owner closure); and an infrastructure control (exit 2).

**Why some expected sets have more than one label (the cascades).** (a) A bound file that fails verification (a wrong digest, a missing file, or a path that is not the contract's) leaves every decision that names it unevidenced: D1 to D6 name the specification, so `bound.sha.spec`, `bound.missing.spec` and `bound.path.spec` bring six `evidence.files.*` labels with them (the last also `bound.path.spec` when the path is wrong), and a changed plan (`bound.sha.plan`) brings `evidence.files.OP-1`. (b) A decision that is missing or not confirmed leaves unmet every accepted case that depends on it: D3 missing brings `op2.depends.E-PIN-14` and `E-PIN-15`; D2 rejected brings its status label, the disagreement with the statement (while the statement still says CONFIRMED) and `op2.depends.E-PIN-04`. (c) A closure record over missing OP-1 evidence names both the closure fault and the unmet evidence. **How the sets were made:** each is the observed output of the check on that fault, read by the author and accepted only if every label follows from the planted fault: **regression pins of the behaviour the author judged right, not an independent proof**; an independent review of each set is what would make them one.

## 6. Not shown, stated

* The owner's statement is transcribed; this repository cannot authenticate it.
* OP-1's strict reader rules are not itemised by the statement; the specification text is missing.
* **The base commit is, by default, a declared identifier**: without `--verify-git` the check does not prove that the commit exists or that the bound files are part of its tree (it checks the current digests, which is a different claim, and says so in its output); the git verification is available and tested, and is the stronger reading.
* The check shows that the record is consistent with its sources and bound files, not that the decisions are right.
* **The positive controls use a FIXTURE of the OP-1 specification text.** They show that the structure and the integrity rules accept a complete package; they are not a check of the content of the real OP-1 specification, which only a review can judge (the check's own test of that text is a lower bound on the presence of the topics).
* The line of the check about D7 and D8 is computed from the review file (the cases that depend on them), not printed unconditionally; the self-test of the real state follows the record (before the OP-1 specification text is recorded it expects NOT_READY for exactly that reason, afterwards a complete package).
* No normative extension exists; the 47 cases are accepted in content only.
* The coverage accounting of the merged plan (#54) still counts the extension through the requirement links, not the verifying cases: a separate follow-up, not done here.
* The proof-of-time chain (expiry 2026-12-31 13:22:39 UTC) is a separate decision branch, not part of this package.
